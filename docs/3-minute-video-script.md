# GridWise Energy Optimizer - 3-Minute Video Script

Target duration: 2:45-3:00 at a natural speaking pace.

| Time | Visuals | Voiceover |
|---|---|---|
| 0:00-0:20 | Title card: **GridWise Energy Optimizer**. Show a campus, solar panels, a battery, and a grid connection. | "GridWise solves a practical smart-campus scheduling problem. For one 24-hour scenario, we receive hourly demand, solar availability, electricity tariffs, battery limits, and one to three natural-language operator notes. The goal is to understand those notes, produce a valid schedule, and minimize the total cost of grid electricity." |
| 0:20-0:42 | Architecture diagram: `POST /optimize-energy` -> `LLM interpreter` -> `Deterministic guardrails` -> `SciPy optimizer` -> `24-hour plan`. | "The core design is a three-stage pipeline. First, a language model interprets the operator notes. Second, deterministic code validates and applies the resulting directives. Third, a linear-programming optimizer schedules grid power, solar usage, and battery actions for all 24 hours. The LLM handles language; it never directly controls the mathematics." |
| 0:42-1:15 | Show a sample note and its JSON interpretation. Highlight `[13, 14]` and `factor: 0.2`. | "For example, a note saying that solar output will drop to about 20 percent from 1 PM to 3 PM becomes a `solar_reduction` directive for hours 13 and 14, with a usable-solar factor of 0.2. The model is also required to return exactly one interpretation for every note, in note order. Irrelevant notes become `no_op`, so a distractor does not invent a constraint." |
| 1:15-1:48 | Zoom into `directives.py`. Animate checks: allowed type, ordered hours, numeric range, `applies`, adjustment shape. | "The model output is treated as untrusted structured data. Pydantic validates the request, then deterministic guardrails check the response shape, supported directive type, note mapping, unique ascending hours from zero through 23, and all numeric ranges. They enforce the semantics that `no_op` is the only non-applicable type, while every real directive must apply. Supported rules include solar reduction, battery reserves, no-charge and no-discharge windows, and maximum grid windows." |
| 1:48-2:23 | Show a simplified LP: variables for grid, solar, charge, discharge, and battery energy. Display the energy-balance equation and a cost curve. | "After normalization, the optimizer builds a linear program using SciPy's HiGHS solver. It minimizes the sum of hourly grid energy multiplied by the hourly tariff. Every solution must satisfy the energy balance: grid plus solar plus battery discharge equals demand plus battery charge. It also respects effective solar availability, battery capacity and reserve, hourly charge and discharge limits, directive-specific caps, and end-of-day battery neutrality. That last rule prevents the starting battery energy from being used as free energy." |
| 2:23-2:43 | Show `POST /optimize-energy` response with `directive_interpretation`, `hourly_plan`, `total_cost_bdt`, and `peak_grid_kwh`. Then show a replay-check icon. | "Before returning the response, the service cancels any simultaneous charge and discharge, independently replays the schedule hour by hour, and rejects any violation. The API returns the interpretation, all 24 hourly actions, total grid energy, total cost, peak grid usage, and a short summary." |
| 2:43-2:58 | Terminal recording: setup, health check, tests, and live sample command. | "To run it locally, create a virtual environment, install `requirements-dev.txt`, set `GROQ_API_KEY`, and optionally set `OPENROUTER_API_KEY` for backup failover. Start `python -m uvicorn app.main:app --reload --env-file .env`. Organizers can verify readiness with `curl.exe http://127.0.0.1:8000/health`, run the automated suite with `pytest`, and exercise the real model with `python -m scripts.smoke_groq --all`. Docker Compose is also available as a fallback." |
| 2:58-3:00 | Closing card: **Language understanding. Deterministic safety. Mathematical optimization.** | "GridWise turns flexible operator language into safe, reproducible, cost-aware energy schedules." |

## Recording notes

- If the live model call is slow, show the command and a previously captured successful response while keeping the automated test output visible.
